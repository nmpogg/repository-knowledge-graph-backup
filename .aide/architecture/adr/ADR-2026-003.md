# React + Vite single-page web application

## Context and criteria

The MVP needs an interactive graph explorer, evidence drawer, onboarding/job states
and conversation workspace served locally from the same origin as the API. M0 must
work against fixtures and M3 must switch to the live API without rewriting screens.

## Options considered

1. React + Vite SPA with a typed `RkgClient` mock/live boundary.
2. Server-rendered templates with progressive JavaScript.
3. A desktop wrapper in the MVP.

## Decision

Use React + Vite, produce static assets served by `CMP-RKG-TRANSPORT`, and keep all
network access behind one typed `RkgClient`. Mock and live clients implement identical
contract shapes. Fonts/icons are bundled locally; repository/model text is escaped or
sanitized according to content type.

API v1 uses bounded polling for job progress and a complete response for Q&A. The UI
shows pending/progress/error states; it does not simulate token streaming. SSE,
WebSocket and a desktop wrapper are outside the MVP contract.

## Consequences and guardrails

- API enums and limits are imported/generated from the contract, never duplicated by
  component-local strings.
- Graph canvas has a keyboard-accessible list/detail fallback.
- Dialog focus, live status announcements, reduced motion and 375–1440 px layouts are
  gate criteria, not optional polish.
- M0 fixture acceptance is distinct from M3 live integration acceptance.

## Implementation status

Revision 1, pinned by `approval-005`, is the decision above: transport serves the
Vite build on the same origin. The current server does not. `rkg serve` runs
uvicorn, the Vite dev server is separate, and the API does not mount frontend
assets. This revision does not reverse that decision. Keeping it, or replacing
it, needs an architecture decision. `CMP-RKG-TRANSPORT` revision 6 describes the
running processes.
