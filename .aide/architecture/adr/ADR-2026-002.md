# Kùzu embedded graph store for the MVP

## Context and criteria

RKG needs local single-user operation, directed typed traversal, persisted snapshots,
evidence properties, bounded queries and durable conversation state without requiring
an external database service. The store must support atomic publication and pinned
reads while keeping installation small.

## Options considered

1. Kùzu embedded property graph.
2. SQLite tables/recursive CTEs with an application graph layer.
3. NetworkX/in-memory graph plus a separate persistence store.
4. Neo4j or another standalone graph server.

## Decision

Use Kùzu embedded behind `CMP-RKG-GRAPH`. `TBL-RKG-GRAPH` owns semantic schema and
`DDL-RKG-GRAPH.cypher` is the physical bootstrap contract. One application process
owns all writers. `CMP-RKG-GRAPH` owns schema/migration, graph publication and the
storage façade; `CMP-RKG-CONVERSATION` persists turn/state through that façade on the
same database — not via a second embedded instance or unmanaged connection.
Readers pin `snapshot_id` for the whole request. Version and client library are
pinned in `TASK-RKG-001`.

## Rationale

Kùzu directly models typed nodes/relationships and keeps deployment embedded. SQLite
would reduce dependencies but move traversal/schema semantics into application code;
NetworkX would require a second durability model; a standalone server conflicts with
the local-first operational constraint.

## Consequences and guardrails

- MVP server runs one application worker. Multi-process access requires a new ADR and
  concurrent-start/write/recovery evidence.
- Schema migrations open a previous-version fixture; dropping a user database is not
  an upgrade strategy.
- Search normalization/index strategy and DDL syntax are verified against the pinned
  Kùzu version before Contract Gate.
- If Kùzu cannot meet migration, atomicity or benchmark requirements, the decision is
  revisited; artifacts must not silently fall back to an in-memory graph.
